NESA — Technical Blueprint
Architecture, data model, scheduling engine, Android strategy, security, and implementation boundaries
1. Technical Objective
Build NESA as a maintainable, modular Android-first application whose deterministic core remains reliable offline. AI and network capabilities are extensions around the core rather than dependencies of it.
2. Recommended Architecture
Presentation layer: modern declarative Android UI, preferably Jetpack Compose.
Application/domain layer: use cases, scheduling engine, activity state transitions, goal logic, and module orchestration.
Data layer: local database plus repositories.
Platform layer: Android alarm/notification/background APIs, usage access where permitted, audio/haptics, and device capabilities.
AI/network layer: isolated services that can be disabled without breaking the core.
Dependency injection: use a standard DI approach such as Hilt.
Architecture should follow clear boundaries so UI never directly manipulates persistence or platform services.

5. Scheduling Engine
The scheduler is the central deterministic engine. It receives activities, constraints, priorities, flexibility, recurrence, deadlines, user preferences, and current state. It outputs a proposed timeline and explicit change reasons.
5.1 Scheduling rules
Protect fixed/critical anchors.
Respect sleep target unless the user explicitly overrides it.
Preserve deadlines.
Place high-priority flexible activities before normal/low-priority activities where feasible.
Use time-flexible activities to fill suitable gaps.
Move day-flexible activities to another day when the current day cannot reasonably contain them.
Use the evening as a recovery/overflow zone.
Never silently delete an important activity.
When multiple solutions exist, prefer the least disruptive change.
Explain meaningful automatic changes.

7. Offline-First Rules
All core writes go to local persistence first.
UI observes local state through Flow/reactive repositories.
Network failures never prevent core schedule viewing or alarm execution.
Sync, when introduced, must reconcile rather than overwrite blindly.
AI requests are queued or gracefully unavailable offline.
8. Alarm System
Use exact alarm facilities only where appropriate and allowed by Android.
Alarm configuration must survive process death and device restart where platform rules allow.
Handle timezone and daylight-saving changes safely.
Persist alarm state before scheduling platform alarms.
Provide a recovery path if Android revokes or restricts an alarm capability.
Wake challenge must be local and lightweight.
9. Notifications
Use notification channels by category.
Allow per-module notification control.
Use escalating reminders only according to guidance personality.
Do not create notification spam.
Respect Android notification permission requirements.
10. Screen-Time / Focus Technical Boundary
Android usage monitoring can use permitted usage statistics mechanisms. App restriction/blocking depends on Android capabilities, permissions, device manufacturers, and implementation choices. The product must degrade gracefully where hard blocking is unavailable.
11. AI Architecture
Create an AIProvider interface independent of Gemini.
Create a Gemini implementation behind the interface.
AI receives structured NESA context rather than raw database access.
AI proposes actions as typed commands.
An action validator checks permissions and constraints.
High-impact actions require confirmation unless explicitly authorized.
The deterministic scheduler performs actual schedule changes.
AI output should never directly execute arbitrary code or database queries.
12. Voice
Voice should initially be treated as an input/output layer over the same assistant command system. Wake-word support is a later capability and must account for Android background restrictions, battery usage, privacy, and microphone permissions.
13. Security
Never hard-code API keys in source control or a distributed production build.
For a personal prototype, local secrets may be injected through secure development configuration, but the architecture must support a backend proxy before public release.
Encrypt sensitive local data where justified.
Use least-privilege Android permissions.
Log technical failures without logging unnecessary personal content.
Separate debug tooling from production builds.
14. Android Compatibility
Target modern Android while maintaining a deliberate minimum supported API level. Native/compiled dependencies should support common ARM ABIs, especially armeabi-v7a and arm64-v8a if the chosen dependencies permit. Build configuration should generate the appropriate APK/AAB artifacts rather than maintaining separate application codebases.
15. UI/UX System
One primary action per screen where practical.
Timeline is the main surface.
Progressive disclosure: advanced settings appear only when needed.
Use consistent cards, spacing, typography, iconography, and motion.
Light/dark variants share the same information architecture.
Do not fill screens with dashboards unless the data helps a decision.
Accessibility: scalable text, adequate touch targets, semantic labels, contrast, reduced-motion consideration.
16. Testing Strategy
Unit-test scheduling rules heavily.
Test activity state transitions.
Test alarm scheduling/rescheduling logic.
Test recurrence and timezone edge cases.
Test missed/skip/later behavior.
Test schedule collisions and anchor protection.
Test offline operation.
Test permission-denied scenarios.
Test low-end Android performance.
Run regression tests after every stage.
