NESA — Claude Build Instructions
A staged engineering prompt and operating contract for building the application
How to use this document
Give Claude the relevant stage prompt only after the previous stage has passed its gate. Claude must inspect the existing code before changing it, preserve working behavior, and stop when a stage is complete rather than inventing the next stage.
1. Master Engineering Contract
You are the primary implementation engineer for NESA, an Android-first adaptive personal assistant. Build the application incrementally and preserve architecture quality.NON-NEGOTIABLES:1. Inspect the existing project before making changes.2. Do not rewrite working systems unnecessarily.3. Do not implement future-stage features early unless a small architectural hook is required.4. Keep the core offline-first.5. Keep business logic out of UI composables.6. Use typed models and clear repository/use-case boundaries.7. Do not hard-code secrets or API keys.8. Do not give AI direct database or arbitrary code execution access.9. Write tests for important deterministic logic.10. After implementation, run/build/test what is possible and report exact failures.11. If a requirement conflicts with Android platform limitations, explain the limitation and implement the safest graceful fallback.12. Never claim a feature works unless it has been verified.13. Keep the interface premium, modern, calm, and uncluttered.14. Prefer simple robust solutions over clever complexity.15. Before adding dependencies, justify them and verify compatibility.
2. Product Rules Claude Must Preserve
NESA is an adaptive personal assistant, not a rigid task list.
Balanced guidance is the default.
Skipped and missed activities are different.
Fixed anchors are protected.
Flexible activities can move.
Evening is an overflow/recovery zone.
Night prepares tomorrow and protects the sleep target.
Users are not forced to configure unused modules.
AI suggests and orchestrates; deterministic application logic validates and executes.
Core functions must remain useful without internet.
3. Stage 1 Prompt — NESA Core
Build Stage 1 only.GOAL:Create a reliable offline-first NESA core capable of onboarding, showing a daily timeline, managing activities, adapting flexible activities around fixed anchors, delivering a smart alarm, and running a wake challenge.REQUIRED:- Android project with maintainable modular architecture.- Kotlin and modern Android UI.- Local persistence.- Minimal onboarding with goals and wake/sleep basics.- Timeline screen.- Add/edit/delete activity.- Activity priority and flexibility.- Fixed anchor support.- Basic adaptive scheduling engine.- Activity states: upcoming, active, completed, later, skipped, missed, cancelled.- Smart alarm configuration.- Local wake challenge.- Snooze/retry policy.- Notifications.- Light/dark system theme plus initial NESA green theme.- Settings.- Unit tests for scheduling and state transitions.UX:The first launch must not ask the user to configure every NESA module. Let users enter the application quickly. Modules are configured when activated.SCHEDULER:Protect fixed anchors. Move flexible activities when possible. Preserve sleep target. Use the evening as recovery space. Explain meaningful automatic changes.ALARM:Do not depend on the internet. The wake challenge should be short and accessible. Do not use a difficult mathematical challenge by default.STOP CONDITION:Do not implement fitness, screen-time enforcement, AI, voice, cloud sync, or advanced personalization in Stage 1.
4. Stage 1 Verification Checklist
Fresh install launches successfully.
User can finish onboarding without configuring optional modules.
User can add an activity.
User can mark an activity fixed/flexible and assign priority.
Scheduler can move a flexible activity without moving a fixed anchor.
Missed and skipped states behave differently.
Timeline survives app restart.
Alarm configuration persists.
Wake challenge works offline.
Notifications work under supported Android permissions.
Light/dark/system theme behavior is correct.
Tests pass.
5. Stage 2 Prompt — NESA Life
Build Stage 2 on top of the verified Stage 1 code.ADD:- Work schedules.- School schedules.- Training schedules.- Recurring activities.- Day-of-week rules.- Prayer/reminder module as optional.- Meals as optional activities.- Richer daily recovery.- Evening overflow handling.- Night review.- Missed-activity review with suggested rescheduling.- Daily/weekly basic statistics.RULES:Never make these modules mandatory. A user can enable them independently.NIGHT REVIEW:Show what was completed, skipped, missed, or moved. Suggest sensible destinations based on priority, flexibility, deadlines, and tomorrow's anchors.Do not add AI yet. Suggestions must come from deterministic rules.
6. Stage 3 Prompt — Health, Learning & Focus
Build Stage 3 only after Stage 2 passes its gate.FITNESS:- Optional module.- Collect goals, experience, equipment, ability, and relevant self-reported constraints.- Provide beginner/intermediate/advanced starting pathways.- Build workouts from structured exercise data.- Track completion and difficulty.- Progress gradually.- Include rest days.- Never make medical claims.LEARNING:- Allow learning sessions and skill goals.- Allow external resources/links without pretending NESA owns those services.FOCUS:- Use Android-supported usage monitoring where permissions are available.- Let users configure thresholds and intervention personality.- Offer break prompts and productive alternatives.- Implement hard restrictions only where platform permissions and APIs support them.- Provide override/fallback behavior.Do not add AI yet unless required solely to preserve an abstraction boundary.
7. Stage 4 Prompt — NESA Intelligence
Build Stage 4 after Stage 3 is stable.ADD:- AIProvider abstraction.- Gemini adapter.- Structured assistant commands.- Read schedule capability.- Create activity.- Move activity.- Reschedule activity.- Suggest schedule.- Explain schedule.- User-controlled permission system.- Confirmation for high-impact changes.- Secure API architecture suitable for future public deployment.- Voice input/output as an optional interface if platform support is reliable.CRITICAL:The model must never directly execute arbitrary database operations.AI outputs structured intents. NESA validates the intent against permissions and scheduling rules. The deterministic application layer executes the approved action.If API credentials would be exposed in the client, stop and redesign around a secure backend/proxy before treating the implementation as production-ready.
8. Stage 5 Prompt — Personalization & Polish
Build Stage 5 only after all prior gates pass.ADD:- Theme engine.- Multiple curated themes.- Light/dark variants for each theme.- System theme selection.- Custom primary color with derived palette.- Optional background image.- Widgets where practical.- Advanced personalization.- Accessibility polish.- Performance optimization.- Animation/motion polish.- Empty states, error states, permission states, onboarding refinement.- Final visual consistency pass.Do not clutter the interface. Personalization must not change the core information architecture.
9. Claude's Debugging Protocol
Reproduce the problem.
Identify whether it is UI, domain logic, persistence, Android platform behavior, or integration.
Write or update a regression test when practical.
Make the smallest correct fix.
Run the relevant tests/build.
Check that previously working behavior remains intact.
Report what changed and what was verified.
10. Claude's Definition of Done
Feature implemented according to the stage specification.
UI is coherent with the NESA design system.
State persists correctly.
Offline behavior is verified where applicable.
Error and permission states are handled.
Tests cover important deterministic behavior.
Build succeeds or failures are explicitly documented.
No secrets are committed.
No future-stage feature was accidentally introduced.
Stage gate checklist is satisfied.
11. Final Instruction to Claude
NESA is intended to grow over time. Your job is not merely to make the current screen work. Your job is to leave behind a codebase that another engineer can safely extend.When uncertain, prefer:- explicit state over hidden behavior,- deterministic rules over magic,- modular boundaries over shortcuts,- local reliability over network dependency,- user control over coercion,- accessible defaults over specialized assumptions,- tests over confidence,- and maintainability over speed.Do not declare a stage complete until its verification checklist has been addressed.
